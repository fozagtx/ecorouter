Security model

What the contract checks, in what order, and what is not done yet.

Read this first

EcoRouter is on Stellar testnet only and the contracts are not audited. Use test funds. Do not rely on it to protect real money.

The principle

The agent proposes. Only the contract authorizes. The app, the assistant and agents all pre-check payments so you see problems early, but those checks are a convenience. The rules that decide whether money moves are in the team-account contract, which holds the funds and runs every check itself.

Check order in pay

pay(spender, service, amount, memo, key) runs these checks in this order. The first one that fails stops the call and nothing is transferred.

#CheckFails whenErrorCan a person ask for approval?
1Account pausedThe owner paused the team account.AccountPausedNo
2Spender existsThe caller is not a spender.UnknownSpenderNo
3Spender pausedThe owner paused this spender.SpenderPausedNo
4Policy expiredThe policy's expiry has passed.PolicyExpiredNo
5Amount > 0The amount is zero or negative.InvalidAmountNo
6Service on allowlistThe service id is not on this spender's list.ServiceNotAllowedYes
7Replay key unusedThis key was already used.DuplicatePaymentNo
8Per-payment capThe amount is above max_payment.OverPaymentCapYes
9Payments per periodThe spender already made max_payments this period.OverFrequencyYes
10Allowance leftThe amount is above what is left this period.OverAllowanceYes
11Registry resolvesThe id is unknown or suspended in the registry.UnknownService, ServiceSuspendedNo
12Balance covers itThe account holds less than the amount.InsufficientFundsNo
13Transfer + receiptUSDC moves to the resolved payee and a pay event is emitted.

When a check fails, the call fails and nothing moves. If the failing rule is one of the four marked "Yes", the app shows the payment as held and a person can file an approval request for it. An agent cannot file requests (AgentCannotRequest), so for an agent every failure is a refusal. The contract's check function runs the same rules as a dry run, which is how the app shows the arithmetic before you sign.

The spender must also authorize the call with its own Stellar signature, so no one can pay on another spender's behalf.

Settling an approved exception

Approving a request and moving money are separate transactions. settle refuses if the account is paused, the request is not approved or has expired (requests last 7 days), the service no longer resolves, or the balance is too low, and it refuses if the service's payee changed since the request was filed. An approval covers one payment, to one payee, for one amount. Settled exceptions do not count against the spender's allowance.

Assistant pipeline

Requests typed in plain words pass through five stages before reaching pay: sentence, assistant, schema, registry, policy. The output schema has no address field, so an invented recipient cannot be expressed. See Assistant.

What is not done

Be clear about the current limits:

  • Not audited. No third party has reviewed the contracts or the app.
  • Testnet only. There is no mainnet deployment. Test USDC only.
  • The registry owner controls the registry. It registers services and can suspend them. A suspended service stops receiving payments from every team that uses it until it is resumed. Teams trust the registry owner for this.
  • A payee can rotate its payout address. Ordinary payments after a rotation go to the new address. Approved exceptions are protected: settlement refuses if the payee changed after the request, but in-policy payments are not held for a payee change.
  • Agent keys are hot keys. An agent's key lives wherever the agent runs. The policy bounds the damage, so keep agent policies tight.
  • The sandbox is a mirror. It runs a TypeScript copy of the contract's rules for demos. It is not a security boundary, and the contract is the source of truth if they ever differ.

Reporting a problem

Open an issue on GitHub. For anything sensitive, ask for a private contact in the issue rather than posting details.
