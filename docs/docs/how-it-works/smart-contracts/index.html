Contracts reference

Public functions, types, events and errors of the team-account and service-registry Soroban contracts.

Two Soroban contracts make up EcoRouter on Stellar. Both live in the repository under contracts/.

ContractPathPurpose
team-accountcontracts/team-accountHolds the team's USDC, stores a policy per spender, runs the checks and pays.
service-registrycontracts/service-registryResolves a service id to the address that gets paid.

This page summarizes the public interface. The Rust source in contracts/ is authoritative. Amounts are in the asset's atomic units (USDC has 7 decimals). Times are ledger timestamps in seconds.

team-account

Construction

__constructor(owner, asset, registry) sets the owner, the token contract to pay in (USDC) and the service registry. The account starts unpaused with no spenders.

There is no deposit function. To fund the account, transfer USDC to the contract's address; balance() reads the contract's token balance.

Owner functions

All of these require the owner's signature.

FunctionEffect
set_policy(spender, input: PolicyInput)Creates a spender or fully replaces its policy. A new spender starts a fresh period; an existing one keeps its period, usage and pause state. Fails with InvalidPolicy if any limit is not positive, max_payment > allowance, expires_at is not in the future, or more than 32 services are listed.
set_spender_paused(spender, paused)Pauses or resumes one spender.
remove_spender(spender)Deletes the spender's policy and usage.
set_paused(paused)Pauses or resumes the whole account. A paused account authorizes nothing, including settlement of approved requests.
withdraw(to, amount)Moves USDC out of the account.
approve(id)Approves a pending, unexpired request. Moves no money.
decline(id)Declines a pending or approved-but-unsettled request.
propose_owner(new_owner)First step of an ownership transfer. The new owner calls accept_owner().

Spender functions

FunctionAuthEffect
pay(spender, service, amount, memo, key) -> ReceiptspenderRuns the checks below, transfers to the payee the registry returns, and emits a pay event. There is no recipient parameter. key is a 32-byte one-time key chosen by the caller, so a retried submission can never pay twice.
request_approval(spender, service, amount, memo) -> u64spenderFiles a request for a payment that one of the exception-eligible rules refused. People only. Records the rule, how far over it was, and the payee the registry returns now. Nothing moves. Requests expire after 7 days.
settle(id, caller)owner or the spender who filed itPays an approved request. Refuses if the account is paused, the request is not approved or has expired, the service no longer resolves, the payee changed since the request was filed (PayeeChanged), or the balance is too low. Settled exceptions do not consume the spender's allowance.

Check order in pay

  1. Account paused → AccountPaused
  2. Spender exists → UnknownSpender
  3. Spender paused → SpenderPaused
  4. Policy expired → PolicyExpired
  5. Amount > 0 → InvalidAmount
  6. Service on the spender's allowlist → ServiceNotAllowed
  7. Replay key unused → DuplicatePayment
  8. Per-payment cap (max_payment) → OverPaymentCap
  9. Payments per period (max_payments) → OverFrequency
  10. Allowance left this period → OverAllowance
  11. Registry resolves the service → UnknownService, ServiceSuspended or RegistryUnavailable
  12. Balance covers the amount → InsufficientFunds
  13. Transfer, then the pay receipt event

Rules 6, 8, 9 and 10 are exception-eligible: a person whose payment fails one of them can call request_approval. Agents get AgentCannotRequest.

Dry run

check(spender, service, amount) -> Verdict runs the same rules without auth or state changes and returns { rule, over_by, allowance_left, period_spent, period_count }. rule is 0 when the payment would go through, otherwise the error code that would refuse it. The app uses this to show the arithmetic before anything is signed.

Building

Both are standard Soroban crates. Build and deploy with the Stellar CLI (stellar contract build, stellar contract deploy) against testnet. Deploy the registry first, then the team account with the registry's address.

Team account

One shared USDC account, held by a Soroban contract, that every spender pays from.

Security model

The team-account contract checks each payment and remains the source of authorization.
